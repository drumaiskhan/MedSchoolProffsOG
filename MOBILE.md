# Mobile apps (Capacitor)

`artifacts/frontend-student` and `artifacts/frontend-admin` are now also
Capacitor projects. Same React/Vite code, same `pnpm run build` output — this
just wraps that build in a native iOS/Android shell so it can go through the
App Store and Play Store, and so the reader can use real OS-level screenshot
blocking (`FLAG_SECURE` on Android) instead of the JS-only deterrents in
`BookReader.tsx`.

**I scaffolded the config; I did not run it.** This container has no network
access and no Xcode/Android SDK, so `ios/` and `android/` don't exist yet —
those are generated by the CLI commands below, which need to run somewhere
with both.

## What's here vs. what you still need to generate

Committed:
- `capacitor.config.ts` in both frontend packages
- Capacitor deps + `cap:*` scripts in both `package.json`s
- `src/lib/nativeScreenshotGuard.ts` in both apps, wired into
  `BookReader.tsx` (student, per-screen) and `main.tsx` (admin, global)

Not generated yet (needs a machine with Node, and Xcode for iOS / Android
Studio for Android):
- `artifacts/frontend-student/ios/`, `.../android/`
- `artifacts/frontend-admin/ios/`, `.../android/`

## First-time setup (per app)

```bash
cd artifacts/frontend-student   # or frontend-admin
pnpm install
npx cap add ios       # needs Xcode + CocoaPods, macOS only
npx cap add android    # needs Android Studio / Android SDK
```

Before running these: **the `appId` in `capacitor.config.ts` is a
placeholder** (`com.medschoolproffs.student` / `com.medschoolproffs.admin`).
It becomes your bundle ID / package name on both stores and is painful to
change after your first TestFlight/Play Console upload — pick the real one
now if you have one in mind.

## Building for real (every time the web app changes)

```bash
pnpm run cap:sync      # = vite build, then `npx cap sync`
npx cap open ios       # opens Xcode — build/run/archive from there
npx cap open android   # opens Android Studio
```

`cap sync` copies the fresh `dist/public` into both native shells and
updates native plugin registrations. Run it after every change before
testing on device — Capacitor doesn't watch the web build automatically.

## Required env var: `VITE_API_BASE_URL`

The native app has no "same origin" to fall back to — there's no backend
co-located with it the way local dev proxies `/api` to `localhost:3001`.
Set `VITE_API_BASE_URL` to your production API URL (e.g.
`https://your-api.up.railway.app`, no trailing `/api`) when running
`pnpm run cap:sync` / `pnpm run build` for a native build, the same way
Vercel/Netlify split deploys already do (see `DEPLOYMENT.md`).

## The one thing to test hardest: cookie auth on iOS

`sessionCookieOptions` in `artifacts/api-server/src/lib/auth.ts` is
hardcoded `SameSite=None; Secure` for cross-site cookies (frontend and API
on different domains). That's fine in a normal cross-site browser fetch.
Inside a WKWebView on iOS it's a known flaky spot — Apple's tracking
prevention sometimes drops cookies for requests to a domain other than the
WebView's own origin, config workarounds (`androidScheme: 'https'`, which
I've set) help but aren't a guarantee, and this genuinely varies by iOS
version. **Test login → refresh → still-logged-in on a real iOS device**,
not just the simulator, before shipping.

If it breaks: don't fight iOS on this. Switch the native builds to bearer
tokens instead of cookies — the plumbing already exists and was clearly
built for this:
- `lib/api-client-react/src/custom-fetch.ts` has `setAuthTokenGetter()`,
  whose own comment says it's for exactly this case (token-gated calls
  from a non-browser client), and it attaches
  `Authorization: Bearer <token>` automatically once registered
- you'd need the login endpoint to also return the raw token in the JSON
  body (not just set it as a cookie) when the request comes from the native
  app, and store it with `@capacitor/preferences` (or the Keychain via a
  secure-storage plugin) instead of relying on `credentials: 'include'`

I didn't build this out since it's a real auth-flow change, not a config
tweak — happy to do it if the cookie test above fails on device.

## Also update: CORS allow-list

Add the native app's effective origin to `APP_URL` on the API host once you
know what it resolves to on-device (`https://localhost` is the default with
`androidScheme: 'https'` set — confirm by logging `Origin` on a real
request, native WebView origins aren't always exactly what the docs imply).

## Screenshot blocking — what's actually guaranteed

| | Android | iOS |
|---|---|---|
| Blocks the screenshot itself | ✅ `FLAG_SECURE` — real OS-level block | ❌ Apple provides no API for this, full stop |
| Blocks screen recording | ✅ | ❌ (can only detect after the fact, not in this build) |
| Hides content in app-switcher thumbnail | ✅ | ✅ |

Student app: guard is scoped to `BookReader.tsx` only (mount = enable,
unmount = disable) — nothing else in the app is affected.
Admin app: guard is enabled globally at startup, since exam answer keys and
unpublished questions show up on most admin screens, not one page.

The per-page watermark in `api-server/src/lib/bookReader.ts` remains the
real backstop on iOS — same as it already is on the web.

## Store review notes (once you get there)

Not done yet, flagging so it's not a surprise: app icons/splash screens
(Capacitor ships placeholders), privacy nutrition labels (Apple) / Data
safety form (Google) — screenshot-blocking libraries don't collect data
themselves, but your API does — and, for the student app, Apple's
subscription/IAP review if payments happen in-app (`payments-admin`
suggests they currently go through some other rail; if so, make sure that's
still allowed on iOS or you'll need Apple IAP for it).
